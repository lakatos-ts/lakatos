# CLAUDE.md

Thales is lakatos's proof tool: the `thales` executable, a Lean program (`lake build thales`). Its sources are Lean and it is not an npm package (its suites and check scripts run from the repo root); it reaches lemma, the TypeScript front end, as a subprocess. (Running one file on the evaluator behind the same typecheck gate is `tarski <file.ts>`, from this same package; see the semantics section below.) Annotated TypeScript is emitted as plain Lean 4, Lean attempts to prove each `@ensures` property against a model of each function, and one SZS verdict per annotation comes back as a JSON envelope.

Three Lean libraries, one tool:

- **`Thales/`** — the tool: `thales [files-or-globs...]`, `--help`, and `run-artifact <file.lean>` (one artifact's parsed verdict channel, for the check scripts). It starts lemma through `Tarski.Lemma`, reads lemma's v1 documents, renders each artifact in process, runs `lake env lean` per artifact, joins the channels, and prints the envelope as `Lean.Json`. Start at `Thales/Prove.lean` (the spine) and `Thales/Cli.lean`.
- **`ThalesDsl/`** — the prover, built on the JS-semantics library in `Js/` (read the semantics section below before touching it); artifacts import it and are run with `lake env lean`. Start at `ThalesDsl/Prove.lean` (the tactic ladder) and `Js/Runtime.lean` (the semantic domain). Toolchain pinned in `lean-toolchain`; `lake-manifest.json` is tracked.
- **`ThalesEmit/`** — the renderer, called in process by `Thales/`: lemma's emission in, a readable `.lean` artifact out. The emitter itself (tsc AST → per-declaration JSON, and the classification of what it cannot map) is lemma's, `lemma/src/emission.ts`: its output is the `emission` of a `lemma check` document, and the invariants below are thales's contract with it. Its unit tests are lemma's; `tests/emission-corpus.test.ts` pins what it emits for this package's fixtures and corpus.

Annotation parsing is not here: discovery, extraction, and prefix/formula parsing live in `lemma/`; the Lean side never sees Lemma syntax.

Docs under `docs/adr/`, `docs/specs/`, `docs/beyond-typescript.md`, and `CHANGELOG.md` predate the plain-Lean rewrite and still describe the removed whole-file compiler (its own, earlier `Thales/` library and `thales` executable, TH-code diagnostics). Trust the code, not those. `CONTEXT.md` holds the engine's vocabulary.

## Common commands

From `thales/`:

```bash
lake build                       # every library and all three executables
lake build Test                  # every Lean test under Test/, the semantics' too
lake env lean Test/ThalesDsl/BindersTest.lean # one Lean test file in isolation
lake build thales                # just the thales binary
```

From the repo root (the tests and check scripts run there):

```bash
npm run build                      # lemma's bin, which the binary and the check scripts run
npx vitest run thales/tests        # the suites; the bin suites skip without LAKATOS_PROVE_E2E=1
npm run format:check               # prettier, whole repo, one config
LAKATOS_PROVE_E2E=1 npx vitest run thales/tests/e2e.test.ts   # full prove e2e (needs Lean)
npm run check:verdict-channel      # verdict-line contract over thales/tests/fixtures/*.lean
npm run check:envelopes            # the binary's envelopes against stored expectations
                                   # (LAKATOS_PROVE_E2E=1 adds the corpus manifest)
UPDATE_ENVELOPES=1 LAKATOS_PROVE_E2E=1 npm run check:envelopes   # regenerate the store
```

Run the binary from a project directory (where `tsconfig.json` is) with `LAKATOS_LEMMA` set to this checkout's `lemma/` (built): `LAKATOS_LEMMA=/path/to/lakatos/lemma timeout 600 /path/to/lakatos/thales/.lake/build/bin/thales <file.ts>`.

After changing `ThalesDsl` or `ThalesEmit`, rebuild with `lake build thales`: the run's own `lake build` builds only the default target, so the binary and the `ThalesEmit` library it loads would stay stale.

Always wrap `lake env lean` invocations in a timeout when running them by hand; a bad artifact can grind indefinitely. The check scripts build and run the binary (`scripts/harness.js`): the verdict channel goes through `thales run-artifact`, the envelopes through a staged project per fixture with `LAKATOS_LEMMA` set to this checkout's lemma, so the sentinel, the parse, and the lake invocation are production's, never a copy.

## The prove pipeline

`Thales.prove` (`Thales/Prove.lean`, behind `Thales/Main.lean`) is one spine over lemma's documents:

1. **Admit** — `Thales/Admit.lean`: `Tarski.Lemma` runs `lemma check` over the patterns (or the files tsconfig.json compiles) and decodes the v1 documents. A refused run (a program that does not compile, a rejected pattern) prints lemma's notes and exits 2; otherwise each file's annotations are partitioned into those lemma already classified (malformed, type faults, unexported references: `InputError`, `Inappropriate`, `NotTried`) and those that go to Lean. A file whose annotations are all classified gets no artifact.
2. **Mirror** — `Thales/RunDir.lean`: one directory per invocation, `.lakatos/<UTC time>` (`-2`, `-3` when two runs share a millisecond), with each artifact at its source path under `thales/`. A pattern naming a file outside the current directory is refused (exit 2).
3. **Render + run** — `Thales/Engine.lean`: `lake build` once, then per artifact the renderer runs in process (no budget) and `lake env lean` checks the result (timeouts: build 600 s; artifact 300 s plus 120 s per `#thales_validate` line). Each artifact carries one `#thales_validate` per entry-module function and constant, whose `thales-model:` line is read beside the verdicts. A failing or timed-out artifact is that file's failure; the run completes and healthy verdicts still ship.
4. **Join** — `Thales/Join.lean` and `Thales/Channel.lean`: verdict lines are matched to annotation identities; missing, duplicate, surplus, or unrepresentable statuses make the run unhealthy (`NotTried` envelope, stderr diagnostics, exit 2). The same join puts each `thales-model:` line onto every annotation of its declaration as the envelope's `model` field: a proven annotation always carries one, a declaration the artifact stated no obligation for is `unvalidated` with that as its reason, and a duplicate line is unhealthy like a duplicate verdict.
5. **Print** — `Thales/Envelope.lean`: the envelope is `Lean.Json` (`Json.pretty`: Lean's key order and layout), so consumers compare envelopes as values, never as text or by key order. `version` is `Thales.version`; `startedAt` is UTC with milliseconds. Exit 2 for a refused run, input error, engine `Error`, unhealthy run, or interruption; 1 when a verdict was `CounterSatisfiable` and nothing outranks it; 0 otherwise.

**Interruption is child death only.** An engine child that exits 130, 143, or 129 without thales having killed it is SIGINT, SIGTERM, or SIGHUP, and reports `User`. Thales installs no signal handler: a terminal Ctrl-C reaches thales itself and ends it with no envelope.

### Emitter invariants the code will not teach you

- Everything an annotation's fate can be settled by is settled in lemma's emitter, before Lean. An unmappable construct or an operator outside the model (`**`, the bitwise family) in a signature, a statement, or a formula classifies `Inappropriate`, naming the construct; the engine's own gaps classify `Error`; a safe-integer-clamped range classifies `NotTried` / `unsupported-range`. Classified annotations never reach Lean.
- **Classification travels.** Every declaration the walk cannot model registers as a failed declaration, and a use of it — call, read, binder type, formula atom — reports that declaration's own reason, never "engine broken". Registries are keyed by module and name together.
- **A body degrades on one thing only**: the first statement outside the slice. A refusal at an _expression_ inside a body becomes a residual site instead — a `noncomputable opaque` over the modeled scope, valued in `JsM`, carrying the refusal text as its docstring — and every callable reaching one is tainted `noncomputable` so compiled evaluation cannot prove through it. A `throw` of anything but the seven builtin error kinds (`Error`, `TypeError`, `RangeError`, `ReferenceError`, `SyntaxError`, `EvalError`, `URIError`) is a residual site too — in a constructor a discarded one, since a constructor cannot `return`. Writes (`=`, `++`, `delete`) never residualize: a site would hide the mutation. Formulas never residualize.
- **Rendering is quotations only.** `ThalesEmit` builds every line via `TSyntax` quotation and Lean's pretty-printer, never string concatenation (the one override, `ThalesEmit/Format.lean`, keeps `return` on its argument's line). Each printed obligation is parsed back and its spine compared to the IR (`ThalesEmit/RoundTrip.lean`), so renderer drift fails the emission by name instead of degrading a verdict.
- **Names never collide by construction.** Models live under `TsModel` with call sites qualified; a dependency's models take its entry-relative path as one guillemet component; a binder spelled like the artifact's own vocabulary (`pure`, `ballIco`, `Float`, `self`) is primed; a source binding of `NaN`, `Infinity`, `undefined`, `null`, `Math`, or `Number` shadows the builtin — those are fallbacks, never keywords.
- **Truthiness has no model.** Conditions, `!`/`&&`/`||` operands, and `Object.is` arguments must be boolean-shaped; a number is refused there. Unions and optionals ride the wire as one `JsVal` binder; reads at a number position are the throwing projection `JsVal.toNumber` — the model refusing coercion, not a claim JS throws.
- **The emitter never writes an AST node.** The `ast` field is the bridge's output, statements selected whole from the closure's modules; `ThalesEmit` decodes it with `Tarski.Decode` and renders the decoder's `Program`, so the artifact's `TsModel.f.ast` is what the evaluator would run, not the emitter's reading of `f`. A closure that will not close — a binding renamed on import, one name declared by two of the closure's modules, a name one module uses free that another declares — carries no field at all rather than a node the emitter authored.
- Emitted artifacts pin `set_option autoImplicit false`: they run under lean's defaults, not the lakefile's options.
- `scripts/check-envelopes.js` compares projected envelope entries to `tests/fixtures/envelopes.expected.json`; `UPDATE_ENVELOPES=1` insists on the full manifest so the store never goes partial. Rendering rules are pinned as syntax guards in `Test/ThalesEmit/RenderTest.lean`; the goldens under `tests/fixtures/*.emitted.lean.expected` are readability pins only. **A new emission shape adds a guard, not a golden.**

## The verdict channel

Each `#thales_prove` prints exactly one line: `thales-verdict:` + compact JSON `{identity, szs, reason, axioms?, counterexample?}`. Stdout is also Lean's diagnostic stream; only sentinel-framed lines are contract. An empty `reason` is a contract violation, contained like any other malformed line.

- `Theorem` — a rung succeeded. `axioms` names the non-standard axioms the proof rests on (empty for kernel-checked; `native_decide`'s per-proof axiom is reported under the stable spelling `Lean.ofReduceBool`). A true bounded claim under the evaluation cap is a Theorem whenever the budget affords the oracle's own instance synthesis and codegen; `axioms` says whether a rung proved it or the evaluation's held proof shipped.
- `CounterSatisfiable` — false on the bounded domain with a concrete witness (`counterexample`: binder → value). Under the evaluation cap the oracle searches its witness compiled, so a witness anywhere in the range is found; past the cap the kernel-decide rung searches in the elaborator, and falsity established there whose witness the elaborator cannot reach ships without one as `GaveUp` instead: established falsity is never given back for the cost of illustrating it.
- `GaveUp` — the ladder exhausted; the reason carries the residual goal. A rung that blows `maxRecDepth` has failed, the annotation has not: the ladder falls through.
- `Inappropriate` — outside the model, not beyond the engine: an unmapped construct, a refused operator, or a path through a residual site (the reason lists the sites' constructs). `Error` stays reserved for the engine breaking, and names the phase that failed.
- `NotTried` — no structured property (the bare-payload degradation path).
- `Timeout` — the per-annotation heartbeat budget (`thales.heartbeats`, overridable via `LAKATOS_PROVE_HEARTBEATS`; 0 is not a budget and is ignored). Later annotations still run with fresh budgets. A bounded claim under the evaluation cap whose model is computable reaches it only when the budget cannot afford the oracle's own instance synthesis and codegen (the timeout bucket's case); otherwise the oracle settles it before any rung can starve.

### The model channel

Beside the verdicts, each `#thales_validate` prints exactly one line: `thales-model:` + compact JSON `{file, function, status, reason?}`. Two statuses, `validated` and `unvalidated`, and the reason is present exactly when the model is unvalidated — an empty one is a contract violation, contained like any other malformed line. The reasons are the construct a tainted or decoder-refused declaration has no run for, a parameter this slice cannot quantify, the goal that did not reduce, and the budget.

- `thales.validateHeartbeats` is the per-declaration budget, overridable via `LAKATOS_PROVE_VALIDATE_HEARTBEATS` under the prove budget's rule (0 is ignored). `check:envelopes` sets it per fixture: the two quick fixtures run at the real budget, so the store carries one validated model, and the corpus slices at 1, where every declaration reports the budget reason in milliseconds instead of the hours the full manifest would cost. The two gated e2e suites shrink it to 1 for the same reason, with one real-budget test on the tracer; `check:verdict-channel`'s `validate.lean` is where the closer's own behaviour at the real budget is pinned.
- An artifact's lean timeout grows by `VALIDATE_TIMEOUT_MS` per `#thales_validate` it carries, so a file with many validated declarations is not killed for being large.
- **An unvalidated model never moves a verdict.** The command's `simp` can get stuck but cannot refute, so a model line reports what was established about the correspondence and nothing about the properties. The envelope's `model` field joins these lines onto annotations: required on a `Theorem`, carried on the prover's `GaveUp`, `Timeout`, `CounterSatisfiable`, and `Inappropriate`, and on no other status and no refuter entry.

The `Szs` inductive here is the prove pipeline's status set, and `tests/verdict-contract.test.ts` checks that each constructor goes on the wire under its own name. Nothing in this package pins it against the shared vocabulary, the `szs` values of the repo's `spec/envelope.schema.json` (which add the CLI-only `InputError` and `User`): a new status is an edit to both.

The check scripts use `thales run-artifact` for the verdict channel and a staged project per fixture for the envelopes; the envelope store holds envelope projections, compared as values.
- `tests/conformance/` — `.ts` fixtures bucketed by the SZS status every annotation in them must receive, run end to end by `tests/verdict-corpus.test.ts` (gated like the prove e2e). Its README has the bucket conventions.

## Conventions

- **`autoImplicit` is off** in `lakefile.lean`; bind implicit and universe variables explicitly.
- **Failure containment over abortion.** A construct the engine can't handle degrades that declaration, that annotation, or that artifact — never the run. New emission shapes must preserve this.
- **One verdict line per `#thales_prove`, always**, even for failures the elaborator can see. Annotations lemma classifies never enter the channel; the run joins them from each document's annotation outcomes.
- **Boundary rule:** nothing under `Js/` or `Tarski/` may import `ThalesDsl`, `ThalesEmit`, or `Thales`, or mention any emission concern; `scripts/check-imports.sh` enforces the imports in CI, against a planted violation under `scripts/import-fixture/` too.
- **Lean builds here; the tests and check scripts run from the repo root**, whose `package.json` carries `check:envelopes` and `check:verdict-channel`. There is no `package.json` here. Formatting is root-only: one prettier pin, one config.

## The semantics and the evaluator (`Js/`, `Tarski/`)

Tarski is lakatos's JS-semantics library: the Lean definitions that give TypeScript's values and operations their meaning. `thales` proves `@ensures` properties against models built from these definitions. It sits below the prover in this package: nothing under `Js/` or `Tarski/` imports the prover's libraries or mentions any emission concern — lakatos owns syntax and search, this library owns meaning.

It holds two things over one set of definitions. `Js/` is the semantics library. `Tarski/` is an evaluator for a fragment of JavaScript — a definitional interpreter whose every primitive operation _is_ one of the library's, so a `Theorem` and a run appeal to the same meaning. The evaluator's parser is not in Lean: lemma's parser bridge (`lemma/src/estree.ts`, over tsc) emits ESTree JSON, and `lemma/schemas/tarski-estree.schema.json` is the seam. `Tarski/Test262/` is the test262 runner, `tarski-test262`. `tarski <file.ts>` reaches lemma itself, as a subprocess: `Tarski/Lemma.lean` resolves its bin (`LAKATOS_LEMMA=<checkout>`, or the pinned release installed once into `~/.cache/lakatos/lemma@<version>`), runs `lemma check`, and decodes the document, and `thales` and the test262 runner reuse it. Growing the evaluator is GitHub epic #376.

### Common commands

From `thales/`:

```bash
lake build tarski                   # just the evaluator's binary
lake build Test                     # every Lean test; these under Test/Js/ and Test/Tarski/
lake env lean Test/Js/NormTest.lean # one test file in isolation
sh scripts/check-boundary.sh        # the evaluator's arithmetic boundary
sh scripts/check-imports.sh         # Js/ and Tarski/ import nothing of the prover
```

And the test262 runner, `tarski-test262`, which parses through lemma
(`npm run build` at the repo root first):

```bash
lake build tarski-test262
.lake/build/bin/tarski-test262 setup     # fetch the pin into .test262 (or set LAKATOS_TEST262)
LAKATOS_LEMMA=$PWD/../lemma .lake/build/bin/tarski-test262 --slice-file test262/slice.txt
LAKATOS_LEMMA=$PWD/../lemma .lake/build/bin/tarski-test262 --slice-file test262/slice.txt \
  --check test262/expected.json
sh scripts/test262-full.sh               # the scheduled full run; writes test262/results.{md,json}
```

`LAKATOS_TEST262` names a checkout to read instead of `.test262`, and the
runner labels a results table with the commit that checkout is really at.
`--jobs` (default: the core count) bounds the `tarski` children running at
once. `TEST262_TIMEOUT_MS` (default 10000) and `TEST262_BUDGET_MS` (default
14400000, four hours) are what `test262-full.sh` passes as `--timeout` and
`--budget`; the script defaults `LAKATOS_LEMMA` to this checkout's lemma.

The binary lands at `.lake/build/bin/tarski` and takes one ESTree document:

```bash
node ../lemma/dist/cli.js parse t.js | jq .program > t.json   # after npm run build
.lake/build/bin/tarski run t.json    # the completion value is a line of output
.lake/build/bin/tarski exec t.json   # it is not; this is what `tarski <file.ts>` runs
LAKATOS_LEMMA=../lemma .lake/build/bin/tarski t.ts   # one TypeScript file, through lemma's gate
```

The suites that spawn the evaluator's and the runner's binaries are in `tests/tarski/`, run by the root vitest.

Wrap `lake env lean` in a timeout when running it by hand; a bad artifact can grind indefinitely.
